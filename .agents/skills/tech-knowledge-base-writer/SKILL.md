# 技术知识库写作

## 目标

把用户给出的一个技术主题，写成从 0 基础也能循序渐进读懂的中文技术知识体系。输出必须既适合学习，又适合长期沉淀为知识库文档。

优先达成这些结果：

- 形成完整知识地图，而不是零散文章列表。
- 从入门概念逐步过渡到真实项目、工程化、性能、质量和生态。
- 对初学者友好：先解释“是什么、为什么、用来解决什么问题”，再讲 API、原理和最佳实践。
- 图文并茂：在适合的位置使用 Mermaid 图、表格、流程图、结构图、时序图、状态图或知识脑图帮助理解。
- 示例贴近真实项目：代码有上下文，解释关键点，避免只给片段。

## 工作流程

1. 识别用户指定的单一技术主题，例如 React、Vue、Next.js、Vite、TypeScript。
2. 识别用户想要的产物：完整知识库、目录规划、学习路线、单篇文章、实战项目、团队工程手册、面试体系或迁移指南。
3. 如果用户只给技术名，默认生成“面向 0 基础到真实项目开发的完整知识体系”。
4. 先给出知识地图，再给目录结构；如果用户要求写文章，再进入单篇文档。
5. 对版本敏感的内容标注版本范围；无法确认最新版本时，说明需要查证，不要假装确定。
6. 输出前做质量检查：是否始终围绕一个主题，是否覆盖基础、实战、工程化、生态、质量、性能和常见问题，是否有合适图解。

如果用户给出的范围太大或目标不清，但可以合理默认，就先按默认方案继续；只有在技术主题本身不明确或会影响文件落点时才询问。

## 默认输出结构

当用户要求“构建完整知识体系”“设计知识库”“从 0 学习某技术”时，按这个顺序输出：

1. 技术定位
   说明它是什么、解决什么问题、常见应用场景、和前端/后端/工程体系的关系。
2. 学习前置
   说明需要哪些基础；如果面向 0 基础，要补齐必要的 Web、JavaScript、TypeScript、Node.js 或工程常识，但只讲理解该主题必需的部分。
3. 知识地图
   用 Mermaid `mindmap` 或 `flowchart` 展示整体结构。
4. 学习路线
   按“入门 -> 基础 -> 核心机制 -> 项目实战 -> 工程化 -> 进阶专题”组织。
5. 文档目录
   给出可落地到知识库的目录树；如果用于本仓库，使用 `content/<技术栈>/<slug>.mdx` 形式，并提醒同步 `_meta.ts`。
6. 核心模块说明
   简述每一部分要解决的问题、读者学完后应该会什么。
7. 实战项目路线
   设计 1 到 3 个从小到大的项目，把知识点串起来。
8. 图解清单
   标出哪些文章建议放什么图，例如渲染流程图、数据流图、请求时序图、状态迁移图、模块关系图。
9. 后续扩展
   给出高级主题、源码理解、性能优化、测试、团队规范等扩展方向。

## 知识体系分层

为一个技术主题设计知识库时，优先覆盖这些层级：

- 入门认知：技术定位、解决的问题、最小心智模型、常见误区。
- 环境准备：安装、编辑器、脚手架、包管理器、开发服务器、调试方式。
- 基础语法：初学者必须掌握的最小语法集、核心 API 和日常写法。
- 核心概念：组件、状态、路由、渲染、编译、类型、模块、生命周期等与主题相关的关键概念。
- 核心机制：底层工作流、运行时机制、编译构建过程、数据流、缓存、调度或响应式。
- 项目实践：目录组织、模块拆分、组件封装、业务流程、错误处理、权限、表单、请求。
- 工程化：构建配置、环境变量、代码规范、类型检查、Lint、格式化、CI、发布。
- 生态工具：只覆盖该技术生产项目中常见且必要的主流生态，并说明用途、场景、选型理由和注意事项。
- 测试质量：单元测试、组件测试、端到端测试、Mock、覆盖率、回归风险。
- 性能优化：加载、渲染、缓存、拆包、懒加载、监控、定位方法。
- 架构实践：团队规范、可维护性、扩展边界、模块约束、复用策略。
- 常见问题：高频错误、原因、排查路径、修复方案。
- 进阶专题：源码、插件、SSR、框架原理、跨端、微前端、复杂状态或大型项目治理。

## 面向 0 基础的写法

每个新概念首次出现时，按这个顺序解释：

1. 一句话定义：它是什么。
2. 问题背景：没有它会遇到什么问题。
3. 直观类比：用工程或生活中的简单场景帮助理解，但不要幼稚化。
4. 最小示例：给出能运行或能读懂的最小代码。
5. 项目用法：说明真实项目里通常怎么用。
6. 常见误区：说明初学者最容易错在哪里。
7. 下一步：关联到后续知识点。

写作时遵守：

- 先讲结论，再解释细节。
- 每篇文章只解决一个主要问题。
- 少堆术语；术语必须解释。
- 代码示例要标注语言，并包含必要上下文。
- 不要只说“推荐这样写”，要说明适用前提。
- 对复杂主题使用“先会用 -> 再理解原理 -> 最后掌握边界”的节奏。

## 单篇文档模板

编写具体文章时，优先使用这个结构：

```md
# 标题

## 知识定位
说明这个主题在整个技术体系中的位置，以及为什么需要掌握。

## 你会学到什么
用 3 到 5 条列出读者学完后能做什么。

## 核心结论
先给出最重要的判断、规则或使用建议。

## 基础概念
解释必要概念，首次出现的术语要讲清楚。

## 图解理解
使用 Mermaid、表格或结构图解释流程、关系或层次。

## 最小示例
给出最小可理解代码，并解释关键行。

## 项目用法
给出真实项目风格的写法，说明目录、职责和调用关系。

## 工程实践
说明生产项目、团队协作、可维护性方面的推荐做法。

## 常见问题
列出高频错误、原因分析、排查方式和修复建议。

## 进阶理解
补充机制、原理、边界条件或性能影响。

## 相关主题
列出知识库内部应该继续阅读的关联文档。
```

可以根据文章类型删减章节，但不要丢失“定位、解释、示例、实践、问题、关联”这条主线。

## 图文并茂规则

当内容涉及结构、流程、关系、生命周期、请求链路、状态变化、构建过程或知识分层时，必须优先考虑 Mermaid 图解。图要服务理解，不要为了好看而画。

| 场景 | 推荐图表 |
| --- | --- |
| 知识体系、模块层级、学习地图 | `mindmap` 或 `flowchart` |
| 流程、步骤、决策分支 | `flowchart` |
| 请求响应、组件通信、调用交互 | `sequenceDiagram` |
| 生命周期、状态迁移、异步状态 | `stateDiagram-v2` |
| 类、接口、模块关系、数据结构 | `classDiagram` |
| 数据模型、表关系 | `erDiagram` |
| 版本演进、学习路线、项目阶段 | `timeline` |
| Git 分支与发布流 | `gitGraph` |
| 构成占比 | `pie` |

Mermaid 约束：

- 使用基础语法，保证 GitHub、Nextra、VS Code 等主流渲染器容易渲染。
- 图中标签使用中文，技术名词保留英文。
- 每张图只表达一个重点；复杂系统拆成多张图。
- Mermaid `flowchart` 的 `subgraph` 标题不要加引号。
- 图前用一句话说明“这张图看什么”，图后用短段解释关键路径。

除了 Mermaid，也可以使用 Markdown 表格、对比表、目录树、分层清单、代码注释和小结来增强可读性。不要擅自引入自定义 MDX 组件。

## 生态覆盖规则

当用户要求“完整知识库”“开发指南”“实战手册”时，必须覆盖该技术的主流生态。生态内容要围绕用户指定主题展开，只在必要时提及周边工具。

示例：

- React 知识库可覆盖 React、JSX、组件、Hooks、状态管理、React Router、Next.js、Zustand、Redux Toolkit、TanStack Query、Vite、Testing Library、Vitest、性能优化。
- Vue 知识库可覆盖 Vue 3、组合式 API、响应式、组件、Vue Router、Pinia、Vite、Nuxt、VueUse、vue-tsc、Volar、Vitest、Vue Test Utils、常见 UI 组件库。
- Vite 知识库可覆盖开发服务器、依赖预构建、插件机制、环境变量、构建优化、库模式、SSR、Rollup 关系、常用插件。
- TypeScript 知识库可覆盖类型系统、类型收窄、泛型、工具类型、声明文件、工程配置、类型体操边界、与前端框架集成。

不要因为示例中出现其他技术名，就把它们混入用户没有指定的知识库。只有在生态工具、工程实践或迁移对比确实需要时才提及。

## 本仓库写作约定

当需要在本仓库创建或修改文章时，遵守这些规则：

- 文章路径使用 `content/<技术栈>/<slug>.mdx`，允许嵌套。
- 每篇 `.mdx` 的 frontmatter 必须包含 `title` 与 `description`。
- 新增、重命名、删除 `.mdx` 时，同步同目录 `_meta.ts`；键为文件名无扩展名，值为中文标题，顺序为侧边栏顺序。
- 正文使用中文，技术名词和代码保留英文。
- 代码块标注语言。
- 站内链接使用绝对路径，例如 `/react/hooks`。
- 非必要不引入自定义 MDX 组件。

## 质量检查

输出前逐项检查：

- 是否只围绕用户指定的一个技术主题。
- 是否能被 0 基础读者跟上：概念是否解释，前置知识是否补齐。
- 是否形成从基础到高级的知识体系，而不是零散问答。
- 是否包含真实项目示例和工程实践。
- 是否覆盖主流生态、测试质量、性能优化和常见问题。
- 是否在合适位置使用了 Mermaid 或表格，并且图表类型正确。
- 是否避免绝对化最佳实践，并说明适用前提。
- 是否对版本敏感内容给出版本范围或查证提醒。
- 如果写入本仓库，是否满足 frontmatter、路径、`_meta.ts`、站内链接和代码块语言要求。
